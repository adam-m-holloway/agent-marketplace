## Problem

Teams that use Claude Code each grow their own skills and conventions in isolation. There
is no single place to:

- publish a plugin once and version it;
- let teams choose which plugins they consume, or hold a team on a known-good release;
- discover what already exists before building a duplicate;
- see **who depends on which plugin, and who is behind**.

`agent-marketplace`, `team-a` and `team-b` are empty public repos under
`adam-m-holloway`, each with an MIT `LICENSE` and one commit. The target design
(`~/Downloads/plugin-marketplace-tldr.html`, "the guide") is written for an organisation's
GitHub Enterprise. The POC proves the model on github.com at zero cost before it moves
there.

## Solution

`agent-marketplace` is a **Claude Code plugin marketplace monorepo**:

- **Plugins** live in `plugins/<name>/`.
- **Generator.** A zero-dependency Node generator builds the catalogue files from each
  plugin's `plugin.json`, `catalogue.json` and `status.json`.
- **One required CI workflow.** `pr-gate.yml` uses `pull_request_target`, so it always
  runs the **base branch's** workflow file and scripts. It treats the PR's files purely as
  data, with no secrets and a read-only token. A PR therefore cannot change the checks that
  judge it.
  - Script unit tests run after merge, at the start of `release.yml`.
  - `release.yml` then tags each new plugin version `<plugin>--v<version>` and publishes a
    GitHub Release.
- **Catalogue.** A GitHub Pages catalogue (plain HTML + vendored Fuse.js) is built at
  deploy time. It offers fuzzy search, related plugins and copy-button install commands.
- **Authoring.** Authors are steered to **Anthropic's `/skill-creator`**. Its file formats
  are the repo's formats, and the same checks apply either way.
- **Security scanning (an explicit requirement).** Scans for hidden content, dangerous
  patterns and prompt injection, plus gitleaks and SkillSpector, all blocking.
- **Usage insights.** A nightly `insights.yml` reads each consumer's committed settings.
  It records on an orphan `data` branch who uses which plugin, on which channel, at what
  version, since when, and who is behind.

**Two release channels**, as Anthropic recommends: separate marketplace *names* for
separate refs.

- **`agent-marketplace`** (latest) tracks `main`.
- **`agent-marketplace-stable`** follows a `stable` branch, which is moved forward only by
  a reviewed promotion PR.

Per-plugin tags remain for releases and changelogs.

Two **separate** consumer repos reach the marketplace **only via GitHub**:

- **`team-a`** is a Go service on the **latest** channel. It uses `adr-helper` and
  `go-conventions`.
- **`team-b`** is a TypeScript library on the **stable** channel. It uses `adr-helper` and
  `typescript-conventions`.

**The demo:**
1. Release `adr-helper` 1.1.0 to `main`.
2. `team-a` gets it, `team-b` stays on 1.0.0, and insights shows "team-b 1 version
   behind".
3. Promote `stable`, and `team-b` moves to 1.1.0.

**First, a spike (Slice 0)** in a throwaway repo proves the consumption mechanics against
known Claude Code bugs, the channel mechanism, and the insights token.

## Goal

A working, free marketplace that two independent team repos consume, with all of these
working end to end:

- versioning and release channels;
- validation and security scanning;
- discovery;
- usage insights.

It should move to GitHub Enterprise Cloud by changing the owner and auth, not by
redesigning.

## Architecture notes

### Prerequisites (local)

- **Node 24** and **git ≥2.31**.
- **Claude Code ≥2.1.292** for `--marketplace`, and ≥2.1.269 for `plugin eval`. 2.1.319 is
  installed.
- **uv** (for SkillSpector locally) and **Go 1.27** (for `team-a`).
- **`gh`, authenticated with the `repo` and `workflow` scopes.** (No spike repo, so no
  `delete_repo`.)
- **Optional for `npm run check -- --full`:** gitleaks, actionlint and zizmor.
- macOS or Linux.

### Verified facts (2026-11-07)

**Validator and CLI** (local experiments)
- `category` and `tags` belong in the marketplace entry. Unknown entry fields (`stage`,
  `owner`) fail `--strict`. Hence `catalogue.json` and `status.json`.
- `claude plugin validate` needs no login. It doesn't open plugin files when validating a
  marketplace, so each plugin is validated too.
- `claude plugin tag` creates annotated `{name}--v{version}` tags, checks that the
  manifest and the entry agree, and needs a clean tree. There is no `install --version`
  (#63986).
- `claude plugin install --marketplace <src>` registers the marketplace in **user**
  settings only.

**`claude plugin eval`** (docs; v2.1.269+)
- `<case>/prompt.md` frontmatter allows only `max_turns`, `allowed_tools`, `model`,
  `timeout_seconds` and `tags`.
- `graders/<name>.md` take `type` = `regex`, `tool_used`, `tool_order`, `file_exists`,
  `llm` or `baseline`.
- Flags: `--eval-dir --json --no-publish --max-cost-usd`.

**skill-creator** (read from the official plugin)
- `skills/<s>/evals/evals.json` =
  `{skill_name, evals:[{id, prompt, expected_output, files?, expectations[]}]}`.
- The trigger set is `[{query, should_trigger}]`, about 20 queries. It is exported to
  `~/Downloads`, so we keep it at `skills/<s>/evals/trigger-evals.json`.

**Consumption limits and open bugs** (web research; Slice 0 proves or works around each)
- A marketplace `ref` serves **every** plugin from that commit. Release channels need
  **different marketplace names** (host-marketplace docs). A single name in two repos
  probably clobbers one machine's clone (#63682).
- `extraKnownMarketplaces` applies only after folder trust. `-p` needs trust already
  accepted (`hasTrustDialogAccepted`) and `CLAUDE_CODE_SYNC_PLUGIN_INSTALL=1`.
- **#83422:** project-enabled plugins can load nothing without an install record.
  **#87667:** project installs stay on their install-time version. **#76467:** a ref change
  can be ignored. Background auto-update is off by default.

**GitHub** (docs)
- **`pull_request` workflows run the PR's own workflow file**, so a PR can rewrite its
  checks. **`pull_request_target` runs the base branch's file** and gets base context. It
  is safe only when PR content is treated as data: no PR code execution, no secrets, a
  read-only token, and no shared caches.
- Rulesets are free on public repos and can exclude branches. "Required workflows"
  rulesets are Enterprise/org-only.
- `GITHUB_TOKEN` is scoped to its own repo. Reading other public repos is undocumented but
  works in practice, so Slice 0 proves it. The limit is 1,000 requests/hr. The traffic API
  is not available.
- Pages' `github-pages` environment allows only the default branch by default.
- `pull_request*` events don't fire on label changes unless `labeled`/`unlabeled` are
  listed.
- Scheduled workflows on public repos are disabled after 60 days without activity.

**Tooling**
- `skills-ref` is "demonstration only" and rejects non-spec frontmatter, so it was dropped (Q34).
- SkillSpector: `uv tool install "git+https://github.com/NVIDIA/skillspector.git@v2.11.2"`,
  `scan --no-llm`, exit 1 when risk >50, and `--baseline` support.
- gitleaks: use the binary (the action needs a licence for orgs). zizmor: use the CLI (the
  action uploads SARIF).

**Prior art**
- `multi-ai`'s `scan.mjs` contributes the pattern rules plus malicious/benign fixtures.
- `marketplace-main` contributes:
  - a shared commit-msg hook;
  - single PR comments located by a marker;
  - SkillSpector baselines with reasons;
  - issue forms;
  - a `SECURITY.md`;
  - the skill description rule (what / when / triggers / not-for).

### Release channels, promotion and rollback

- **Promotion** (`npm run promote [<main-sha>]`):
  1. Cut `promote/<date>` **from `stable`**.
  2. `git read-tree` it to `main@sha`'s tree and commit.
  3. Open a squash PR into `stable` titled `chore(stable): promote main@<sha>`, with each
     plugin's version change listed in the body.

  The diff is exactly stable→main@sha, so it cannot conflict.
- **Promotion check** (in the `plugins` job, for PRs into `stable`):
  - the head branch is `promote/*`;
  - its tree equals the tree of the `main` commit named in the title;
  - if the **fallback** channel mechanism is in use, the generated stable catalogue is the
    one file allowed to differ, and `promote` regenerates it.

  Promoting a `main` commit **older** than `stable`'s current source requires the
  `rollback` label.
- **The channel mechanism, proven in Slice 0.**
  - **Primary:** both catalogue files exist on every branch, and stable consumers use
    `"ref": "stable"` + `"path"` to the stable catalogue.
  - **Fallback:** the catalogue `name` is derived from the branch.
- **A bad release on `main` (roll forward):**
  1. Revert the change by PR.
  2. `npm run bump <p> patch` (versions are never reused) and merge; a new tag follows.
  3. Latest consumers update, using the commands in `docs/consuming-plugins.md`.
  4. Stable consumers are unaffected unless that version was promoted. If it was, promote
     the fix, or promote an older commit with `rollback`.

### Insights scan

For each repo in `insights/consumers.json`:

1. **Read** `.claude/settings.json` via the Contents API.
2. **Match** the marketplace entries whose `source.repo` is ours and whose name is a known
   channel.
3. **Resolve** the channel ref → SHA → `plugin.json` version.
   - `versions_behind` counts `<p>--v*` tags newer than that version (0 by definition on
     latest).
   - `first_seen` is the first commit touching the settings file.
4. **Write** today's rows, and derive **events by diffing against the previous day's
   snapshot file**, so a same-day re-run is idempotent.

**Clean-answer rule.** `removed` only when the file loads (or returns 404) without our
marketplace. A 403, a 5xx or a rate limit gives `unknown`, and the previous data is kept.

**Token.** The default `GITHUB_TOKEN` if Slice 0 proves it can read other repos.
Otherwise a fine-grained read-only PAT (`INSIGHTS_TOKEN`). Its expiry date is recorded in
`docs/repo-setup.md`, and a failed scan says "token invalid or expired" in the run
summary.

**Honesty.** Insights measures **committed intent per repo**, not what each laptop has
installed (#87667). "Since" means first committed to settings.

### CI design (one required workflow)

**`pr-gate.yml`.**
- **Trigger:** `pull_request_target` on `main` and `stable`, types `opened`, `synchronize`,
  `reopened`, `edited`, `labeled` and `unlabeled`.
- **Permissions:** `contents: read` only, with no secrets and **no caches**.
- **Checkouts:** the base into `./base`, and the PR head into `./pr` with
  `persist-credentials: false`.
- **Execution:** only base scripts, plus pinned tool downloads, read `./pr` as data. **No
  PR code is executed.**
- **Exception:** zizmor's `dangerous-triggers` finding is acknowledged with a written
  reason in `docs/security-scanning.md`.

| Required job | Runs |
|---|---|
| `plugins` | validate `--strict` (catalogues + each plugin), frontmatter, catalogues up to date, version bump + changelog, name consistency, evals + structure, SKILL.md ≤500 lines, schemas + taxonomy, one plugin per PR (unless labelled `multi-plugin`), promotion check |
| `security` | hidden content, dangerous patterns + injection (`rules/patterns.json`), gitleaks **on the PR's files** (`gitleaks dir`, not git history), SkillSpector `--no-llm` (risk >50 fails; baselines honoured; baseline changes flagged) |
| `workflows` | actionlint, zizmor CLI, every action SHA-pinned |
| `title` | the PR title against `.githooks/commit-msg` |

Every job has `timeout-minutes`. Tool installs are pinned release downloads with a single
retry. The CLI is installed at a pinned version with `DISABLE_AUTOUPDATER=1`.

**`release.yml`** (push to `main`, `contents: write`, `fetch-depth: 0`):
1. `npm test` (post-merge script tests). If it fails, the release stops.
2. For each plugin whose version has no tag: `claude plugin tag --push`, then
   `gh release create` with that version's CHANGELOG section.

**`pages.yml`** (push to `main` or `stable`, plus a call from insights) builds and deploys
the site. `stable` is added to the `github-pages` environment's allowed branches.

**`insights.yml`** (nightly cron + dispatch):
- **Permissions:** `contents: write`, used to push `data` only, plus `pages: write` and
  `id-token: write`.
- **Runs:** under a concurrency group, from the default branch.
- **Writes:** the last successful run's date to the summary.
- **Post-POC (Q29):** `issues: write` too, for the behind issues and the pinned daily report
  issue (`scripts/insights/issues.mjs`). `pr-gate`'s `plugins` job also logs
  `base/scripts/triage.mjs` output (data only, never fails).

### Slice 3: `npm run check` (M)

- [x] **Complete** (PR #1; 14 rules, seeded-defect fixtures)

**Path.** `check.mjs` runs every rule and reports all failures together, with file and
line. `--full` adds `npm test` and whichever of gitleaks, SkillSpector, actionlint and
zizmor are installed. The rules are the `plugins` and `security` rows of the CI table:

1. Stale catalogues.
2. **Version bump.** Changed plugin files without a semver increase vs the base (≥1.0.0
   for new plugins). Promotion PRs are exempt.
3. No CHANGELOG entry for the current version.
4. **Name consistency.** Folder ≠ manifest name, a reserved prefix, or `evals.json`
   `skill_name` ≠ SKILL.md `name`.
5. **Hidden content:**
   - Unicode tag characters U+E0000–E007F;
   - zero-width characters U+200B–200D, U+2060, U+FEFF;
   - bidi controls U+202A–202E, U+2066–2069;
   - HTML comments in Markdown;
   - long base64 blobs;
   - `data:` URIs.
6. **Patterns** (`rules/patterns.json`).
   - **HIGH (fails):**
     - pipe-to-shell;
     - destructive `rm -rf` on `/` or `~`;
     - decode-and-execute;
     - remote eval;
     - credential-file reads;
     - a secret sent over the network;
     - an environment dump piped to the network;
     - "ignore previous instructions";
     - "do not tell the user";
     - an unpinned `npx`/`uvx` MCP launcher.
   - **MEDIUM (reported only):** raw-IP URLs and `.env` reads.
7. **Evals.**
   - `evals.json`: the schema, ≥3 cases, unique ids, a non-empty prompt, ≥1 expectation,
     `files` exist, no placeholders.
   - `trigger-evals.json`: ≥8 true and ≥8 false, with no duplicates.
8. SKILL.md is over 500 lines.
9. **Schemas and taxonomy.** `catalogue.json`/`status.json` fail their schema, a category
   or keyword is off-taxonomy, or languages ≠ `any` without `compatibility`.
10. More than one `plugins/*` directory changed without the `multi-plugin` label (CI
    only).
11. The promotion check (CI only, PRs into `stable`).
12. The PR title fails `.githooks/commit-msg` (CI only). Locally, the hook checks commit
    messages via `git config core.hooksPath .githooks`.

**MUTATE:** one seeded fixture per rule. The benign fixtures produce zero HIGH. Deleting a
rule fails its test.
**Evidence:** `npm test` lists one passing test per rule. `npm run check` passes on the
clean tree.
**Depends on:** Slices 1–2.

## Post-POC: staged approval process (Q28 — designed; mostly built, see status below)

The only POC preparation is that stage lives in its own `status.json`.

1. **Who approves.**
   - `CODEOWNERS`: `plugins/*/status.json @adam-m-holloway @<org>/<admins TBC>`. The same
     owners for `CODEOWNERS`, `taxonomy.json`, `rules/`, `scripts/` and
     `.github/workflows/`.
   - **The `main` ruleset gains:** require code-owner review, dismiss stale approvals, and
     require approval of the last push.
   - **Catch:** authors can't approve their own PRs, which is why the team is needed.
2. **What evidence is required.** A `stage-gate` rule in the `plugins` job, for PRs that
   change `status.json`:

   | Move | Gate |
   |---|---|
   | new plugin | starts at `sandbox` |
   | sandbox → incubating | checks green; evals + trigger set; owner named; no HIGH findings; SkillSpector clean or baselined |
   | incubating → published | ≥14 days **or** ≥2 active consumers; a committed eval result for this version; a CHANGELOG entry; no open `bug` issues |
   | → deprecated | `replacedBy` or a reason |
   | → retired | **retire check:** no active consumers in `latest/consumers.json`, or the `retire-anyway` label |
   | any move | one step at a time; only `status.json` (+ generated files) changes |

3. **How a move is requested.** `npm run stage <plugin> <stage>`, plus a "Promote plugin"
   issue form. A bot posts the readiness checklist but never opens the PR itself.
4. **The queue.** "Ready for promotion" and "blocked" sections in the report.
5. **Stages × channels.** The stable channel lists **only published and deprecated**
   plugins.

**Rejected:** labels as the stage, GitHub Environments, a Projects board, Backstage.
**Effort:** about 1–2 slices.
